# TelegramMediaFilter 功能建议报告

- 日期：2026-11-05
- 基线：Telegram Android 13.1.1 (7237) fork，`master` 当前提交 `dce8b161`
- 范围：仅讨论这个 fork 的增量功能，不重复上游 13.1.1 已带的 Communities、Gram 钱包、礼物、RichMessage 等能力

## 1. 结论

当前 fork 已经有“下载队列 + 下载页 + 媒体库筛选 + PikPak 转发 + 独立翻译”这套骨架，继续加零散按钮的收益不高。下一步最值得做的是把**手动筛选、下载、转发**变成规则化、可追踪、可清理的闭环。

优先级建议：

| 优先级 | 功能 | 一句话理由 |
|---|---|---|
| P0 | 自动下载 / 自动转发规则引擎 | 把现有下载队列和 PikPak 转发变成自动化，价值最高 |
| P0 | PikPak 转发任务状态与重试 | 现在只发消息不追踪结果，失败不可见 |
| P1 | 存储生命周期管理 | 下载越多，清理和导出越重要 |
| P1 | 批量选择增强 | 现有范围多选还缺少“全选/反选/按条件选” |
| P1 | 下载调度策略 | Wi-Fi、充电、时段、限速，直接改善日常体验 |
| P2 | 媒体去重 | 图片/视频重复是媒体库最大的噪声来源 |
| P2 | 本地索引与搜索 | 媒体多起来后，靠翻列表找东西不现实 |
| P2 | 聊天/媒体导出 | 归档、备份、迁移都需要 |
| P2 | 翻译增强 | 现有独立翻译开关可以升级为双语/离线/术语表 |
| P2 | 分享面板快捷入口 | “保存到 PikPak / 下载”从分享面板直达，成本低 |

如果只做一件事：**自动下载 / 自动转发规则引擎**。它同时复用现有的 `DownloadManagerService`、`DownloadController` 和 `SharedMediaLayout` 的 PikPak 入口，改动集中，收益最大。

### 1.1 先澄清：原生已有 vs 本报告增量

你问得对：Telegram 原生已经带了其中一部分“基础能力”，报告里的条目不是全部从零新增，准确说是**在原生基础之上做组合、自动化和 fork 场景补缺**。对照如下：

| 报告条目 | 原生是否已有 | 原生已有的部分 | 报告真正要补的增量 |
|---|---|---|---|
| 自动下载 | 部分有 | 设置 → 数据和存储 → 自动下载媒体：按移动网络/Wi-Fi/漫游、照片/视频/故事/文件、最大文件大小、预加载视频/音乐 | 按会话/文件夹、关键词、发送者、大小区间、每日上限、仅充电/时段，以及命中后直接入队/PikPak |
| 自动转发 | 没有 | 只有手动转发；Business 的自动回复/快捷回复不是通用规则引擎 | 按会话/关键词/类型/大小自动转发到 PikPak 或指定会话 |
| PikPak 转发任务 | 没有 | 无 | fork 专有：发送记录、bot 回复关联、成功/失败状态、重试 |
| 存储生命周期 | 部分有 | 设置 → 数据和存储 → 存储用量：按聊天/类型统计、清理缓存、按聊天例外 | 针对 fork 的已下载媒体库/PikPak 缓存：最大文件、30 天未访问、自动清理、导出 SAF |
| 批量选择 | 部分有 | 聊天消息多选、转发/删除；fork 已有媒体库范围多选 | 按当前筛选结果全选/反选、按日期/大小/类型/聊天选，批量 PikPak/删除/下载 |
| 下载调度 | 部分有 | 自动下载的网络类型和大小阈值；下载队列的暂停/继续 | 仅 Wi-Fi、仅充电、时间段、限速、并发档位 |
| 媒体去重 | 没有 | 无 | 精确 hash + 感知 hash 分组清理 |
| 本地索引与搜索 | 部分有 | 全局聊天/消息搜索 | 对已下载媒体按 caption/文件名/聊天名/OCR 的本地索引 |
| 聊天/媒体导出 | 没有（Android 端） | 无完整导出；桌面端有导出 | HTML/JSON + 媒体、增量导出、按大小分卷 |
| 翻译增强 | 部分有 | 原生消息翻译 | 双语对照、离线模型、术语表、按聊天自动翻译 |
| 分享面板快捷入口 | 部分有 | 系统分享面板 | “保存到 PikPak / 下载”作为分享目标 |
| 下载保险箱/应用锁 | 部分有 | 应用锁、Secret Chats | 加密本地媒体、隐藏于相册、生物识别 |
| 自动更新检查 | 没有 | 应用商店/系统更新；侧载 fork 无 | 检查 GitHub release、应用内下载 |

**结论**：真正属于“原生没有、且值得做”的核心是：**自动规则引擎、PikPak 任务状态、媒体库批量选择增强、下载调度、媒体去重、本地索引/导出、保险箱**。自动下载/存储/翻译/多选这些是原生的“基础版”，报告应写成“增强”，不是“新增”。第 3 节候选表里的 P0/P1 优先级不变，但实现时必须先复用原生设置和数据，不要重复造轮子。

## 4. 重点功能拆解

### 4.1 自动下载/自动转发规则引擎（P0）

**问题**：现在每次都要进媒体库手动筛选、范围选择，再点 PikPak 或下载。对固定关注几个群/频道的用户，重复劳动最多。

**方案**：新增 `AutoRuleController`，规则字段建议：

- 范围：会话 / 文件夹 / 全部
- 类型：图片、视频、文件、音频、全部
- 条件：大小区间、caption 关键词、文件名关键词、发送者、时间范围
- 过滤：跳过 `noforwards`、一次性媒体、已转发过的消息
- 动作：仅下载、仅 PikPak、两者都做
- 约束：仅 Wi-Fi、仅充电、每日上限

**接入点**：

- 新消息：监听 `NotificationCenter.didReceivedNewMessages`，逐条匹配规则
- 下载：调用 `DownloadManagerService.enqueue(messageObject)`
- PikPak：复用 `SharedMediaLayout` 里对 `PIKPAK_BOT_ID` 的发送逻辑，抽成 `PikPakForwardService`
- 存储：新增 `auto_download_rules` 表，跟账号数据库走

**验收**：规则命中后 10 秒内入队；同一消息不重复入队；关闭规则立即停止；`noforwards` 和一次性媒体被跳过；规则列表可测试匹配结果。

**风险**：bot 限流、消息风暴、耗电。需要每规则每日上限和去重键（`dialogId + messageId`）。

### 4.2 PikPak 转发任务状态与重试（P0）

**问题**：`SharedMediaLayout.java:5841-5852` 现在只是把消息发给 bot，然后 toast “已加入队列”；bot 是否收到、是否转存成功、失败原因都不可见。

**方案**：

- 新增 `pikpak_forward_tasks` 表：`dialogId`、`messageId`、`botMessageId`、`state`（queued/sent/succeeded/failed）、`error`、`createdAt`
- 监听 bot 回复消息（`MessagesController` 更新），按 `botMessageId` 关联状态
- 下载页增加“PikPak”tab 或设置页任务列表，支持失败重试、批量重试
- 发送前用 `dialogId + messageId` 去重

**验收**：发 10 条能看到 10 条状态；失败可单独/全部重试；重复发送被拦截。

**风险**：bot 回复格式未确认，需要先抓一轮真实回复样本；bot 可能限流。

### 4.3 存储生命周期管理（P1）

**问题**：`DownloadedVideosActivity` 只有网格、选择和删除，没有“总共占多少、谁最占、哪些可以清”。

**方案**：

- 在 `CachedMediaLayout`/`CacheModel` 上增加统计：总大小、按聊天/类型分布、最大 50 个文件、30 天未访问文件
- 增加自动清理规则：超过 N 天、大于 X MB、保留收藏/置顶
- 导出：选中文件导出到 SAF 目录，保留原文件名/日期前缀
- 删除前排除正在下载的任务，避免误删临时文件

**证据**：`DownloadedVideosActivity.java:44`、`:88`；`CachedMediaLayout.java:69`、`:394`、`:407`。

### 4.4 批量选择增强（P1）

现有 `CachedMediaLayout` 有网格选择，`SharedMediaLayout` 有范围多选，但缺少：

- 全选当前筛选结果 / 反选
- 按日期范围、大小、类型、聊天批量选
- 批量动作：PikPak、删除本地、加入下载

验收：500 条选择不 ANR；计数实时更新；批量 PikPak 复用 4.2 的任务表。

## 5. 不建议做

- **重复实现上游 13.1.1 已有功能**：Communities、Gram 钱包、礼物、RichMessage 已经在上游，fork 再做只会增加 rebase 冲突。
- **破解/绕过 Telegram Premium 或服务端限制**：不稳定，账号风险高，且每次上游更新都可能失效。
- **大改媒体库 UI**：现有 `CachedMediaLayout` / `SharedMediaLayout` 已经能承载筛选、选择、网格，优先加能力而不是换壳。
- **一开始就做 PikPak 官方 API 全量对接**：先做 bot 转发任务状态，跑通后再评估 API；直接接 API 的账号/合规风险更高。
- **root/系统级下载或改包**：维护成本高，和当前 fork 的“可跟随上游更新”目标冲突。

## 6. 建议路线图

- **第 1 批（先做）**：自动规则 MVP（仅下载 + 仅 PikPak）、PikPak 任务状态表、全选/反选。
- **第 2 批**：规则里加入 PikPak 动作、存储统计/清理、下载调度策略、分享面板入口。
- **第 3 批**：精确去重 → 感知去重、本地索引/搜索、聊天导出、翻译增强。

## 7. 如果只做一件事

做 **自动下载/转发规则引擎**。它是把当前“手动筛选 + 手动下载 + 手动转发”变成自动化闭环的关键，而且能直接复用 `DownloadManagerService.enqueue`、`DownloadController` 的队列和 `SharedMediaLayout` 的 PikPak bot 发送逻辑；其他功能大多是在这个闭环上补 UI 或补清理。

## 8. 拿不准 / 没查到

- PikPak bot 的真实回复格式、限流阈值、失败重试语义未实测；4.2 需要先抓样本。
- `CacheModel` 是否能直接给出可靠的文件总大小/最后访问时间，需要在真机上验证。
- 500 条批量选择的性能未在 23127PN0CC 上实测，需专门做一次压力测试。
- GitHub 自动更新如果走私有仓库，token 的作用域和分发方式需要再确认。
- 以上优先级基于代码结构和现有功能判断，不是基于实际使用频率统计。
