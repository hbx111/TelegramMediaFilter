# Turrit 下载与保存策略调研

> 调研对象：Turrit Android 1.9.0.3.1（包名 `org.telegram.group`）
> 调研日期：2026-11-08
> 方法：官方文档/商店说明 + APK 静态字符串与类结构分析
> 注意：Turrit 未公开源码，以下“实现层”结论来自 APK 静态证据；20 倍加速属于官方宣传口径，未做同网络条件实测。

## 1. 结论摘要

Turrit 的下载/保存不是“扫描一个下载目录”这么简单，而是做了三层拆分：

1. **下载任务层**：独立的 `com.turrit.download` 模块，维护下载记录、等待队列、状态、进度和续传位置。
2. **文件存储层**：下载文件有独立目录和“公开/私有”标记；下载内容不会被普通缓存清理。
3. **云端转发层**：PikPak 是独立的“先下载、再转发、等机器人回复”的任务流水线，不是简单分享。

这套设计的核心价值是：**下载记录与播放器缓存分离、任务可恢复、质量版本可管理、PikPak 转发可追踪**。

## 2. 产品层策略

### 2.1 下载加速

官方口径：

- 设置 → 实用工具 → 下载加速，可自定义上传/下载速度倍率，最高 20×。
- 支持“返回应用时自动恢复下载”“仅在 Wi-Fi 下启动下载”。
- 断点续传，应用重启/回到前台后可自动恢复。

来源：[Turrit 官网](https://iturrit.com/zh/)、[Turrit 下载加速实测文章](https://iturrit.com/zh/blog/telegram-secrets-tips-and-tricks)

### 2.2 下载管理

官方描述：

- 提供“下载管理”文件夹。
- 已下载内容不会被自动清除。
- 支持批量保存媒体。

来源：[Google Play 中文页](https://play.google.com/store/apps/details?id=org.telegram.group&hl=zh-CN)、[App Store 页面](https://apps.apple.com/tw/app/turrit-%E9%9B%B2%E7%AB%AF%E7%A4%BE%E4%BA%A4%E5%AE%A2%E6%88%B6%E7%AB%AF%E4%B8%AD%E6%96%87%E7%89%88-%E5%85%A7%E5%BB%BA%E5%8D%B3%E6%99%82%E7%BF%BB%E8%AD%AF%E5%8A%9F%E8%83%BD/id6471781238)

### 2.3 缓存清理

- 新增 1 GB / 2 GB 自动清理缓存档位。
- 清理的是“缓存”，不是“下载管理”里的下载文件。

这条区分很重要：**缓存是可再生的，下载是用户资产**。

### 2.4 保存目的地

从官方描述和 APK 结构看，至少有三类目的地：

1. **应用下载目录**：下载管理里长期保留。
2. **系统相册/公共目录**：保存到相册，走 MediaStore/公开文件夹。
3. **PikPak 云盘**：直接保存到 PikPak，或转发给 PikPak 机器人。

`DownloadInfo.privateFlag` 默认值为 `publicFolder`，说明客户端明确区分“公开文件夹”和“私有目录”两种落盘策略。

### 2.5 视频清晰度

- 播放器右上角可设置默认画质：自动 / 最高画质 / 省流模式。
- 保存/下载时可使用 Telegram 原生的 `ChooseDownloadQualityLayout`，在 `document` 与 `alt_documents` 之间选择。
- 官方 App Store 文案还提到“compressed quality options”。

结论：Turrit 保留并强化了 Telegram 的多清晰度模型，但下载记录仍然按 `documentId` 记录，所以同一视频的不同清晰度天然是不同文件/不同记录；是否合并展示取决于下载管理 UI 的聚合逻辑。

## 3. APK 静态证据

### 3.1 独立下载模块

APK 中存在完整包：

- `com.turrit.download.DownloadActivity`
- `com.turrit.download.WaitDownloadFragment`
- `com.turrit.download.DownloadInfo`
- `com.turrit.download.DownloadInfoDao`
- `com.turrit.download.sheet.*`（下载选项底部弹层）
- `org.telegram.ui.DownloadPathSettingActivity`
- `org.telegram.ui.Components.SearchDownloadsContainer`
- `org.telegram.ui.ChooseDownloadQualityLayout`

这说明下载管理是独立页面 + 独立数据层，不是简单复用 `MediaController` 的保存回调。

### 3.2 下载记录模型

`DownloadInfo` 的字段（静态分析）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `dialogId` | long | 会话 ID |
| `mid` | int | 消息 ID |
| `documentId` | long | 文档 ID |
| `fileName` / `filePath` | String | 文件名/落盘路径 |
| `fileSize` | long | 总大小 |
| `currentDownloadedSize` | long | 已下载大小，用于续传 |
| `state` | int | 下载状态 |
| `waitDownloadOrder` | int | 等待队列顺序 |
| `privateFlag` | String | 公开/私有目录标记，默认 `publicFolder` |
| `hash` | int | 消息/文件校验相关 |
| `duration` / `watchTime` | long | 视频时长/观看进度 |
| `messageData` / `messageObject` | byte[] / MessageObject | 消息快照，便于恢复任务 |
| `date` | long | 记录时间 |
| `fileMime` | String | MIME 类型 |

这张表同时保存了**消息定位信息**和**文件进度信息**，所以下载管理可以脱离聊天列表恢复任务。

### 3.3 DAO 暴露的队列语义

`DownloadInfoDao` 的方法名：

- `getAll()`
- `getDownloadedList()`
- `getUnDownloadList()`
- `getWaitDownloadList()`
- `queryByDocumentId()`
- `insert()` / `insertOrUpdate()`
- `updateStateByDocumentId()`
- `updateWatchTimeByDocumentId()`
- `deleteByDocumentId()` / `deleteList()`

对应的是“已下载 / 未下载 / 等待下载”三态，以及按 `documentId` 查询和状态更新，不是按目录扫描。

### 3.4 队列/续传相关字符串

APK 中可见：

- `Auto resume download ,downloading list size:`
- `maxDownloadRequests`
- `isContinueDownload`
- `waitDownloadOrder`
- `downloaded duplicate file part`
- `reference updated resume download`
- `DownloadSpeedLimited`
- `DownloadSpeedLimitedMessage`
- `ChooseDownloadPath`
- `DownloadPathDesc`
- `ClearDownloadsList`
- `DownloadedFiles`
- `DownloadedFilesMessage`
- `Downloading`
- `AccActionCancelDownload` / `AccActionDownload` / `AccDescrDownloadProgress`

可推断：

- 有最大并发请求数/队列顺序控制；
- 支持断点续传和分片去重；
- 有下载路径设置和限速提示；
- 下载页有独立的已下载/下载中列表和取消操作。

### 3.5 PikPak 是任务流水线

APK 中存在：

- `com.turrit.pikpak.forward.PikpakDownloadForwardTask`
- `PikpakDownloadForwardTaskItem`
- `PikpakDownloadForwardTaskDao`

`PikpakDownloadForwardTask` 状态：

- `STATUS_DOWNLOADING`
- `STATUS_FAILED`
- `STATUS_FORWARDING`
- `STATUS_WAITING_BOT_REPLY`

`PikpakDownloadForwardTaskItem` 状态：

- `STATUS_PENDING`
- `STATUS_DOWNLOADING`
- `STATUS_DOWNLOADED`
- `STATUS_FAILED`

字段包括：

- `taskKey` / `itemKey`
- `messageKey` / `messageHash`
- `messageOrder`
- `documentId`
- `localPath`
- `attachFileName`
- `retryCount`
- `pendingForwardCount`

结论：Turrit 的 PikPak 流程是：

```
加入任务
  → 本地下载（PENDING/DOWNLOADING）
  → 下载完成（DOWNLOADED）
  → 转发给 PikPak 机器人（FORWARDING）
  → 等待机器人回复（WAITING_BOT_REPLY）
  → 成功/失败（FAILED 可重试）
```

它保存 `localPath` 和 `messageKey`，说明下载与转发是解耦的，失败后可以重试，不需要重新从聊天里找消息。

## 4. 对当前 fork 的启示

### 4.1 当前问题

当前 `DownloadedVideosActivity` 的策略是：

- 递归扫描 `Telegram Video` 和 `Telegram Video Public`；
- 只按文件绝对路径去重；
- 没有 `dialogId + mid` 聚合；
- 没有下载任务表；
- 播放器缓存和手动下载混在一起；
- 同一视频的 `alt_documents` 各占一格。

这正好对应之前截图里的“同一视频多个大小版本”问题。

### 4.2 建议的数据模型

```text
download_task
  id
  dialog_id
  message_id
  document_id
  quality
  file_name
  file_path
  file_size
  downloaded_size
  state            -- pending/downloading/completed/failed
  wait_order
  destination      -- app/private/public/pikpak
  created_at
  updated_at

download_group
  dialog_id
  message_id
  primary_document_id
  version_count
  selected_document_id
```

展示逻辑：

- 以 `dialog_id + message_id` 为一张卡；
- 默认展示最高质量/原始版本；
- 角标显示“N 个清晰度”；
- 点开可切换版本；
- 只有用户明确选择下载/保存的文件才进“下载管理”；
- 播放器缓存不进入“已下载”。

### 4.3 PikPak 建议

采用 Turrit 的任务流水线，而不是简单转发：

1. 选中消息 → 创建 `PikpakDownloadForwardTask`；
2. 先下载到临时目录，记录 `localPath`；
3. 下载完成后转发给 bot；
4. 等待 bot 回复，更新 `WAITING_BOT_REPLY`；
5. 失败保留任务和 `retryCount`，允许重试；
6. 成功后清理临时文件。

这比当前“直接 forward 到 bot”更可靠，能解决 bot 未响应、网络中断、重复发送等问题。

## 5. 风险与边界

- Turrit 闭源，无法确认 20× 的具体实现；静态证据只能证明有自定义队列、并发、续传和路径管理。
- “群主关闭保存也能保存”属于官方商店宣传，未在本调研中验证，不建议直接照搬。
- `alt_documents` 的不同清晰度仍是不同 `documentId`；即使采用任务表，也需要 UI 层按消息聚合，否则仍会出现多张卡。
- 下载目录与缓存目录必须物理/逻辑分离，否则“自动清缓存”可能误删用户下载。
